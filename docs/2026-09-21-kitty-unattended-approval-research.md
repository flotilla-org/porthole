# Unattended kitty-image-tests: approval requirements

Research for [Establish unattended kitty-image-tests approval requirements](https://github.com/flotilla-org/porthole/issues/172), 2026-09-21. This is source inspection, not a desktop run or a product-policy decision.

## Baseline and provenance

Robert chose a **provisioned host, usable desktop session and OS permissions already granted**, followed by unattended runs. Missing prerequisites block before execution; login automation and OS-consent recovery are outside this first contract. Standing delegation still needs an enforceable run scope. This applies the [working approval model](https://github.com/flotilla-org/porthole/blob/8a4f93f62866450006a3ed754725acf3748850ba/docs/2026-09-21-approval-model-draft.md), without deciding its remaining authority questions.

Inspected kitty-image-tests at `183c0e120429e047db32d0351d4f4cd53f995c62`. Relevant existing dirty files were `smoke/registry.py`, `smoke/features/placement_relative.py`, `smoke/sections/relative_placements.py`, `tests/test_smoke.py`, and `site/src/data/manifest.json`; these add/change relative-placement coverage, so the working manifest is not exactly the committed suite. Existing site UI edits and untracked working notes/repros were left untouched. Citations below identify committed sources; no dirty-only behavior is presented as committed. Porthole was inspected at `8a4f93f62866450006a3ed754725acf3748850ba`.

## Finite workloads and evidence limits

The manifest hashes structured stages/observations, including interaction tags and visual expectations; it does not encode complete authority, external viewer actions or run deadlines. CLI supports an explicit finite stage list. The runner only warns on a manifest mismatch. Consequently a pinned suite/manifest/stage selection is useful preparation input, not itself an enforced delegation. Dirty-source provenance matters: current metadata records HEAD, not modifications. [Manifest](https://github.com/rjwittams/kitty-image-tests/blob/183c0e120429e047db32d0351d4f4cd53f995c62/smoke/manifest.py#L25-L58), [taxonomy](https://github.com/rjwittams/kitty-image-tests/blob/183c0e120429e047db32d0351d4f4cd53f995c62/smoke/taxonomy.py#L32-L48), [selection](https://github.com/rjwittams/kitty-image-tests/blob/183c0e120429e047db32d0351d4f4cd53f995c62/harness/runner.py#L531-L537), [hash check](https://github.com/rjwittams/kitty-image-tests/blob/183c0e120429e047db32d0351d4f4cd53f995c62/harness/runner.py#L324-L333), [metadata](https://github.com/rjwittams/kitty-image-tests/blob/183c0e120429e047db32d0351d4f4cd53f995c62/harness/runner.py#L232-L255).

Retained-stream is explicitly finite: 12 raw 1920×1080 images, followed by placement refreshes. Viewer timing/resource measurements and rendered pixels require additional instrumentation or assessment. Existing recorded visual observations remain uncertain; manual inspection provides the report's visual conclusions. Unattended artifact acquisition is therefore a useful destination without claiming automated judgment of every image. [Workloads](https://github.com/rjwittams/kitty-image-tests/blob/183c0e120429e047db32d0351d4f4cd53f995c62/docs/retained-image-delivery.md#L53-L71), [baseline](https://github.com/rjwittams/kitty-image-tests/blob/183c0e120429e047db32d0351d4f4cd53f995c62/docs/retained-image-baseline-2026-09-17.md#L49-L58).

Existing tests establish attach-only behavior, explicit-surface selection, checkpoint EOF handling, observation barriers, screenshot-error continuation and producer timeouts through mocks/socket fixtures. They do not establish current OS permissions or rendered output. [Delivery tests](https://github.com/rjwittams/kitty-image-tests/blob/183c0e120429e047db32d0351d4f4cd53f995c62/tests/test_runner_delivery.py#L13-L57), [capture tests](https://github.com/rjwittams/kitty-image-tests/blob/183c0e120429e047db32d0351d4f4cd53f995c62/tests/test_runner.py#L479-L542), [timeout test](https://github.com/rjwittams/kitty-image-tests/blob/183c0e120429e047db32d0351d4f4cd53f995c62/tests/test_runner_policy.py#L274-L303).

## Bounded acceptance scenarios to decide against

These are proposed evaluation cases, not settled policy or claims of current support.

| Scenario | Observable acceptance condition |
|---|---|
| Provisioned, authorized host | A named finite stage selection acquires its required evidence and terminates without human interaction under previously delegated authority. |
| Missing prerequisite | Before test effects, report all knowable missing desktop/OS/delegation/tool prerequisites as blocked; no permission bypass or login recovery. |
| Future or reused target | Bind an allowed fresh window/session to this run; reject ambiguity, substitution or unrelated windows without widening authority. |
| Unsupported checkpoint | Explicitly exclude or block a viewer/stall action without an automated implementation; do not convert no-op acknowledgement into coverage. |
| Evidence failure or stalled peer | Deadline produces incomplete/failed acquisition with preserved available artifacts and reason, independently of any protocol pass. |
| Cancellation or restart | Stop owned work and reconcile surviving resources; preserve shared terminals and evidence, and do not blindly rerun a possibly executed command. |
| Changed workload | A changed suite, stage list or additional viewer is checked against delegation before effects; denial ends or blocks unattended work visibly. |

Open decisions remain the delegated principal and trust boundary, exact permitted workload/target selector, deadline and retry budget, required artifact policy, supported checkpoint automation, and cleanup ownership. They belong in the authority, preparation and lifecycle decision tickets.

Only documentation was changed. No harness tests, live GUI runs, permissions, tokens or services were touched. The parent recorded all four Porthole Rust gates passing on the identical source base; this branch adds no Rust changes.
