# Windows Jackstay graphics handoff

Research for [Define the handoff to native Windows Jackstay graphics](https://github.com/flotilla-org/porthole/issues/153), 2026-09-21. This is a planning handoff, not a backend selection or live Windows graphics acceptance result.

## Finding

The first Beaufort workflow can use Porthole screenshots independently of native Jackstay graphics. Native Windows Jackstay needs a substantial transport/lifetime implementation as well as a capture API choice. Preserve host-owned authorization/source selection and Jackstay-owned resource lifetime. The user's settled requirement is that the agent and terminal persist across RDP disconnect or Windows lock; desktop actions may wait or fail. That does not promise uninterrupted capture or survival across logoff/reboot.

## Contracts to carry forward

The [native backend seam](https://github.com/flotilla-org/jackstay/blob/a1e1420d137394f494e156aa1f3f34d996753f9c/crates/jackstay/src/native.rs) separates captured frames, surface pools, fences and transferable handles. Ring entries carry pool/slot identifiers and readiness values, not raw process handles; setup transfers resources. Resize/format change creates a generation and pool. Exhaustion drops or fails publication rather than overwriting held storage.

The [accepted lease decision](https://github.com/flotilla-org/jackstay/blob/a1e1420d137394f494e156aa1f3f34d996753f9c/docs/adr/0001-acquisition-leases-and-reservations.md) requires an acquired frame to outlive ring reuse, with admission reservations and bounded resources. This is partly beyond the old native-ring vocabulary: current [arena cleanup implementation](https://github.com/flotilla-org/jackstay/blob/a1e1420d137394f494e156aa1f3f34d996753f9c/crates/jackstay/src/acquisition/arena/cleanup.rs) retains deferred GPU claims until completion, retains the original lease on failed handoff, and quarantines claims when completion observation fails. A Windows backend must integrate the acquisition contract, not merely add texture handles to the old ring.

**Minimum handoff proposal for this map:** retain (1) host/Vessel identity and GUI session separately from transient capture-source identity; (2) separately reported screenshot, local CPU media, local native media and remote encoded-media capabilities; (3) host authorization/source selection and an explicit endpoint/transport kind, with no assumption that a Unix socket or serialized HANDLE is universal; (4) capture status and restartable generations independent of agent/terminal lifetime; and (5) evidence of source identity, dimensions, capture time and screenshot result. These are requirements for the later design, not new wire fields to implement now. No local shared texture should become the durable identifier of the agent or its workspace.

## Windows mechanisms and implications

| Question | Primary-source evidence | Consequence for future design |
| --- | --- | --- |
| Window or display capture? | [Windows Graphics Capture](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture) supports window/display items, pooled D3D surfaces, timestamps and size changes. [Win32 window interop](https://learn.microsoft.com/en-us/windows/win32/api/windows.graphics.capture.interop/nf-windows-graphics-capture-interop-igraphicscaptureiteminterop-createforwindow) accepts HWND from Windows 10 1903. [Desktop Duplication](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutput1-duplicateoutput) duplicates adapter outputs and requires a device on the output's adapter. | WGC is a candidate for Porthole's window-oriented sources; duplication is a candidate for output capture. This is an inference, not a selected backend. Host consent, source validation and policy remain outside Jackstay transport. |
| Can captured storage be leased directly? | WGC frames return to their pool on disposal; its guide warns against using their surfaces afterward and describes pool recreation on size/device changes. [Duplication acquisition](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutputduplication-acquirenextframe) requires releasing the prior frame before acquiring another. | Prove that source lifetime can satisfy arbitrary admitted holds, or stage into a Jackstay-owned bounded shareable pool. Do not assume an acquired capture texture has export flags or a lifetime sufficient for consumers. |
| How do resources cross processes? | [CreateSharedHandle](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgiresource1-createsharedhandle) creates NT handles for appropriately flagged resources, with access/security settings and explicit close/duplicate semantics. [DuplicateHandle](https://learn.microsoft.com/windows/win32/api/handleapi/nf-handleapi-duplicatehandle) produces a handle valid in the target process. | Windows setup needs authenticated peer/process identity, typed resource transfer, ownership, cancellation and partial-failure cleanup. Sending the source process's integer HANDLE as bytes does not perform transfer. |
| Which synchronization? | [Keyed mutex acquisition](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgikeyedmutex-acquiresync) grants exclusive resource access and distinguishes timeout and abandoned state. [D3D11 fences](https://learn.microsoft.com/en-us/windows/win32/api/d3d11_3/nn-d3d11_3-id3d11fence) provide shared handles, completed values and completion events. | Decide keyed-mutex versus fence interoperability after checking consumer APIs. Mutual exclusion alone is not a broadcast lease protocol. Producer readiness and every consumer's asynchronous release completion are separate obligations. Timeout is not evidence that the GPU stopped using memory. |
| Which device and generation? | [DXGI adapter description](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/ns-dxgi-dxgi_adapter_desc) exposes adapter LUID. [Device removal guidance](https://learn.microsoft.com/en-us/windows/uwp/gaming/handling-device-lost-scenarios) rebuilds device-dependent resources. Duplication can fail when the session disconnects; access loss on desktop/mode switch requires a new duplication interface. | Negotiate adapter identity, formats and synchronization support; decide rejection versus copy fallback for incompatible consumers. Separate logical stream identity from device/pool generation. Device loss needs an explicit retirement/failure policy, never fabricated successful release. |

These API facts do not establish actual WGC behavior during lock/RDP transitions on Beaufort. Later acceptance must observe it. For the current workflow, capture failure or bounded waiting is compatible with the settled persistence requirement; preserving a dead capture object is unnecessary.

## Decisions for a later graphics map

1. Which first source and consumer pair is required: one HWND, a monitor, Wheelhouse, Katzensteg, or an encoder? What Windows/API/driver baseline and SDR/HDR formats are required?
2. Can WGC or duplication source lifetime satisfy Jackstay leases directly, or must capture stage into an owned pool? What reservation and memory budget bounds resize while old frames remain held?
3. What authenticated Windows setup mechanism transfers resource, fence, mapping and wake handles, with recipient verification and cleanup on cancellation/process death?
4. What producer-ready and consumer-release synchronization works across the chosen D3D consumer APIs? How are multiple consumers, adapter mismatch, device removal and unobservable completion handled?
5. What stream/source generation and retry behavior follows resize, source closure, lock, RDP disconnect/reconnect and device recreation? What delayed-consumer and failure-injection evidence proves no premature reuse?
6. Is cross-host video required next, and if so which Windows encode/decode and republishing endpoints fit the existing bridge? Local D3D handle sharing cannot cross machines. A generic Tender byte stream may carry an encoded protocol, but it does not supply texture import, codecs, media timing or lease semantics.

Native graphics implementation and these backend choices remain outside the first screenshot-based Beaufort work packet. This report is based on source inspection and official API documentation only; no GUI, capture, adapter or device-state changes were performed.
